## 実装

`Sources/TabDeskCore/AXWindowReferenceStore.swift` は、CGWindowIDと別型の `WindowReferenceID` を発行し、同じAX参照を `CFEqual` で照合する。
タイトル・位置・サイズから同一性を推測しない。プロセスの開始ごとに世代を発行し、同じPIDが再利用されても旧世代の通知・終了処理が新世代へ作用しないようにする。
失敗した列挙結果を渡して一括削除する入口は設けず、参照の破棄は明示的に行う。

6つのテストで、再取得した同一参照、旧世代からの問い合わせと削除、別プロセスの参照拒否、未知の通知、削除後のID再発行、他プロセスの維持を検証した。
テストでは権限不要のアプリAX要素を使う。窓としての適格性は呼び手が確認する設計であり、実窓の識別はFixtureによる別プロセスの検証で確認した。

`Tools/PublicAXProbe/Probe.swift` は公開属性の読み取りと通知購読だけを行う。
窓の移動や設定変更は行わず、`AXFullScreen` も読まない。試作段階ではタイトルの代わりに同一タイトルを示す番号を記録する。
`Fixture.swift` は自分の専用窓だけを操作し、`NSWindow` の状態を正解確認用に出力する。
詳しい実行手順は [ProbeのREADME](../Tools/PublicAXProbe/README.md) を参照。

## 実機結果

環境: Apple Silicon、macOS 26.6.2。内蔵・外部画面の既存構成を使い、Fixtureは外部画面上で実行した。

| 操作・条件 | 結果 |
| --- | --- |
| タイトル・位置・サイズが同じ2枚の通常窓 | 別々の参照IDになり、再列挙でも維持 |
| 窓A→Bのフォーカス | `AXFocusedWindow` が対応する参照IDに切り替わった |
| 窓Aのタイトル変更・拡大・元のサイズへ戻す | 参照IDを維持 |
| ネイティブフルスクリーンへ入り、通常状態へ戻す | 同じ参照IDを維持。Fixture自身の状態で遷移を確認 |
| 最小化・復帰 | 一時的な読み取りエラーを記録し、その後は同じ参照IDで再取得 |
| 窓Aを閉じ、同名・同サイズの窓Aを再作成 | 元の参照IDを再利用せず、新しいIDになった。窓BのIDは維持 |
| Chrome、TextEdit、Slack | 各5回の読み取りで参照IDを維持。これらの窓では位置変更・フルスクリーン等の操作は未実施 |

詳細ログはローカルの `build/public-ax-probe/run-bundle/` に保存した。

注意すべき観測結果:

1. 起動直後にはAX窓一覧の要素が `AXApplication` として返り、複数窓を同じ参照と判定してしまう状態があった。`.app` 形式でも観測し、その後の前面表示・再問い合わせでは正常になった。原因は未確定。Probeは役割を確認し、窓でない要素を拒否するよう修正した。
2. 移動・リサイズ・フォーカス・生成の通知は計25件観測したが、今回の閉じる操作では破棄通知を観測できなかった。通知購読が成功しても通知だけを生存判定の根拠にできない。未知の参照を含む生成通知もあるため、通知時の窓の適格性検証と、後からの再列挙が必要。
3. 最小化付近で `AXRole` と `AXWindows` の問い合わせがそれぞれ1回 `cannotComplete` になった。次の読み取りで復帰したため、失敗を閉じた窓と扱うと登録消失につながる。
4. 最小化中に窓のsubroleが一時的に `AXDialog` として観測された。登録候補のフィルターと、登録済みの窓を追跡する条件を同じにしないこと。

以上から「参照IDによる識別は試作で成立する」という結果は得たが、終了・消滅・復旧まで本体を置き換えてよいという合格判定にはまだ達していない。

## フルスクリーン判定

Fixtureの通常状態とネイティブフルスクリーン状態で、次の公開情報を比較した。

| 属性 | 通常の拡大窓 | ネイティブフルスクリーン |
| --- | --- | --- |
| 窓のsubrole | AXStandardWindow | AXStandardWindow |
| 位置が書き込み可能か | true | false |
| サイズが書き込み可能か | true | true |
| フルスクリーンボタンのsubrole | AXFullScreenButton | AXZoomButton |
| ボタンのValue | 取得不可 | 取得不可 |

今回のAppKit窓では違いが見えた。しかし位置が書き込み不可であることは、フルスクリーンであることの一般的な証明にはならない。
ボタンの実装・有無・subroleが全アプリ共通であるとも確認できていない。ヘルプ文の文字列比較や画面サイズ一致だけで置き換えると、言語・アプリ・通常窓の大きさによって誤判定し得る。

提案する次の方針は、窓ID取得の非公開関数を先に置き換え、`AXFullScreen` は暫定維持する段階移行。
本体移行に先立ち、通知欠落時の保守的な生存判定・参照失効後の復旧を実装・検証する。
完全な公開API化を先に求める場合は、フルスクリーン判定の追加調査と対応範囲の決定を優先する。この選択を確認するまで本体の判断方式を変更しない。
