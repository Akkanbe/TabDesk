# 初回リリース計画（2026-09-12）

機能追加を一区切りにし、導入・更新・復旧を確認して初回公開するための提案。
Apple Developer Program は未加入。以下は計画であり、加入・実装・公開の承認や実施を意味しない。

## 配布方針の提案

GitHub Releases で少人数のベータ検証を行い、問題を修正して初回安定版を公開する。
バージョン候補は `v0.1.0-beta.1` → `v0.1.0`。公開前に既存のリモートタグとリリースの重複を確認する。
最初は Apple Silicon 向けの ZIP 配布と手動更新に絞る。Intel 対応、自動更新、課金、同期、新しい操作機能は後回しにする。

一般利用者向けのバイナリ配布は Developer ID 署名・公証済みのものを用意する。
加入前でも文書、配布スクリプト、既存環境での検証は進められる。加入を見送る場合は、当面は自力でビルドできる協力者による検証とし、一般向けバイナリ公開時期を分ける。

Mac App Store は初回の対象にしない。現状は Accessibility による他アプリの操作に加えて `_AXUIElementGetWindow` という非公開 API に依存している。公開 API と Sandbox を求める審査条件から、現在の実装のままでのストア公開には課題があると判断した。直接配布でも将来の OS 変更に対する実機確認は必要。

参考: [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)、[App Sandbox](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox)、[Developer ID 配布](https://help.apple.com/xcode/mac/current/en.lproj/dev033e997ca.html)。

- [ ] ソースの公開範囲とライセンスを所有者が決め、LICENSE と必要な素材・ライブラリの表記を用意する。
- [x] 開発用アプリを上書きしない出力先で Release ビルドを組み立てる。新しい依存は追加せず、既存シェルスクリプトの構成を活用する。
- [x] バージョン・ビルド番号・対象CPU・ソースコミットを記録できる手順を作る。バンドルIDは維持する。
- [ ] 既存ロゴを元にアプリアイコンを同梱し、翻訳リソースとともに開発ディレクトリ外で表示を確認する。
- [x] READMEにインストール、権限設定、基本操作、ホットキー競合と変更、手動更新、終了・復旧・アンインストールの手順を用意する。
- [ ] Accessibility は必須、サムネイルの画面収録権限は任意と明示。権限拒否時の案内も確認する。URLコマンドは既定の無効を維持する。
- [x] 保存データ・ログの場所と扱いを実装から確認して記載。ログに窓タイトルが含まれるため、問い合わせ時の伏せ方を説明する。

## 2. 署名・公証（目安: 1〜2作業日、加入等の待ち時間を除く）

- [ ] 所有者が Apple Developer Program 加入と費用負担を判断し、一般配布を進める場合は加入・証明書準備を行う。
- [ ] Developer ID Application 証明書を用意し、署名情報・公証認証情報はKeychain等で管理。秘密鍵や認証情報をリポジトリへ入れない。
- [ ] 配布モードでは自己署名へのフォールバックを禁止し、必要な証明書がなければ明示的に失敗させる。
- [ ] Hardened Runtime と安全なタイムスタンプを有効にして署名する。例外 entitlement は必要性を確認したものだけに限定する。
- [ ] 署名を検証し、`notarytool` による公証の Accepted を確認する。
- [ ] `.app` にチケットを staple して検証し、そのアプリから最終 ZIP を作成。ZIP自体へのstapleは行わない。
- [ ] 最終ZIPのSHA-256、バージョン、ソースコミットを記録し、以後は同じ成果物をテスト・配布する。
- [ ] 署名・Hardened Runtime適用後もAX操作とホットキーが動くことを実機確認する。

確認: 署名・公証・staple検証に加え、Gatekeeperが有効な別のMacでブラウザから取得したZIPを展開して起動する。開発端末のローカル起動だけで公開可能と判断しない。
開発用証明書からDeveloper IDへの初回移行ではAccessibilityの再許可が必要になる可能性を検証し、手順へ反映する。

参考: [Developer account](https://developer.apple.com/help/account/basics/about-your-developer-account)、[公証の概要](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)、[公証ワークフロー](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)。

## 3. 少人数ベータ（目安: 3〜5人で数日〜1週間）

- [ ] ベータ版の対象環境・既知の制限・復旧方法を添えて配布する。
- [ ] 初回導入: 別のMacでアプリをApplicationsへ配置し、権限未付与→拒否→許可、再起動、設定保存を確認。
- [ ] 主要導線: 1画面／複数画面で画面選択→タブ変更→文字入力。同じアプリの窓が複数画面にある場合も確認。
- [ ] 境界操作: 空タブ、連打、最小化、フルスクリーン、ホットキー変更と競合を確認。
- [ ] 画面変更: 接続解除・再接続、配置変更、操作途中の切断、スリープ・ロック解除後を確認。
- [ ] 復旧: 通常終了で退避窓が戻ること、再起動後の登録再同定と手動復旧を確認。異常終了の検証は専用のテスト窓・設定で行う。
- [ ] 更新: ベータ版から次の署名済み版へ手動更新し、設定・登録・ホットキーを保持できることを確認。
- [ ] 不具合報告にアプリ版、macOS、画面構成、再現手順、必要な範囲の匿名化済みログを集め、再現した不具合を小さく修正する。

ロック中などOSが有効なAX参照を返さない場合の復元は既知の制限。成功と誤表示しないこと、通常操作へ戻った後に利用者が復旧できることを確認し、保証できない条件は文書化する。
対応OSごとの結果と未実施項目を記録し、未実施を合格扱いにしない。

## 4. 初回安定版と運用

次を公開条件とする。

- [ ] 起動不能、設定消失、退避窓を復旧できない問題、通常更新で繰り返す権限不具合などの重大な不具合が未解決で残っていない。
- [ ] 公開対象コミットで既存テスト・ビルドが成功し、追加修正には必要な回帰確認がある。
- [ ] 対応を表明する環境と主要導線で、配布用成果物の実機確認が完了している。
- [ ] 最終成果物の署名・公証・バージョン・ハッシュが一致し、ライセンスと利用者向け文書が揃っている。
- [ ] GitHub Releaseの下書きにZIP、SHA-256、対応環境、変更点、既知の制限、導入手順をまとめ、所有者の公開指示後に公開する。
- [ ] 検証済み旧版と対応する設定バックアップを保持し、不具合時の復旧手順を確認する。古い版への設定互換性は確認なしに保証しない。
- [ ] 初回公開後は不具合修正を優先し、次のパッチ版を `v0.1.1` とする。macOS更新時にはAX・復元・ホットキーを再確認する。

## 着手順と所要期間

まず第1段階の配布準備を実装し、並行して所有者がDeveloper Program加入を判断する。
次に署名・公証済みのベータ成果物を作り、別環境で導入から復旧まで確認してから公開する。
全体はおおむね1〜2週間を目安とし、加入・証明書の準備、検証端末の確保、見つかった不具合の修正期間は別途見込む。

この計画作成ではアプリコードを変更していない。296テストと実機確認は直前の保守修正時の結果であり、配布版の合格を示すものではない。
